## Credentials and confirmations

The writer credential reader is Windows-only and resolves the Windows Profile Known Folder (`FOLDERID_Profile`) through the OS API; it has no non-Windows or environment-variable fallback. It reads one fixed credential file:

```text
<OS-resolved Windows Profile>\AntiSelekPreviewMigration\preview-turso-writer.env
```

The file must contain exactly `PREVIEW_TURSO_DATABASE_URL` and `PREVIEW_TURSO_AUTH_TOKEN`. No CLI credential-path override, `.env.local`, `private/production-rehearsal.env`, generic `TURSO_*`, `DATABASE_URL`, command-line secret, or ambient credential fallback is supported. The target and migration manifest are source-pinned; do not override the database, endpoint, manifest, or migration list at runtime.

A narrowly reviewed setup must resolve the Windows Profile Known Folder through `SHGetKnownFolderPath`, not trust `%USERPROFILE%` or another environment-variable path, then inspect the existing path metadata. Reject reparse points throughout the path. Above the user profile, reject untrusted effective `DELETE_CHILD`, `DELETE`, `WRITE_DAC`, `WRITE_OWNER`, or `GENERIC_ALL` rights; create-only and harmless read/traverse access may remain. The existing Profile parent must also pass its broader untrusted write/delete check. If any existing parent is unsafe, stop for review rather than repairing it. Only after all existing ancestors pass may setup create the one `AntiSelekPreviewMigration` directory directly under the profile, with its protected DACL for the current user, SYSTEM, and Administrators applied at creation. Do not create it with inherited permissions and repair them afterward. Create the credential file empty with its own protected ACL for those same trusted identities, verify both ACLs with the writer's guard, and only then write credential contents. Do not change the ACL of the existing Profile or any other existing parent. Windows propagates changes to inheritable ACEs to existing children, so do not change the existing `private/` tree, Profile, AppData, or LocalAppData ACLs, recursively reset permissions, or use `icacls /T` ([Microsoft ACE propagation guidance](https://learn.microsoft.com/en-us/windows/win32/secauthz/automatic-propagation-of-inheritable-aces)). Create no secret until the dedicated directory and file protections are verified. No directory, credential, or ACL was created or changed during this review.

A read-only diagnostic confirms this machine's existing Profile path and its ancestors pass the current checks; the fixed `Profile\AntiSelekPreviewMigration` directory is absent, so its ACL has not been tested. The former LocalAppData candidate failed at AppData and is no longer part of the fixed writer path. The passing Profile-chain check supports proceeding only to a separately reviewed local setup; it does not verify the new child/file ACLs or authorize a migration. No credential or protected directory exists yet; do not run the writer until the new directory and credential file have been created through that reviewed setup and verified by the writer's guard. Do not bypass the guard, redirect the credential to a fallback path, or change existing parent ACLs under this procedure.

The writer fails closed if the exact Known Folder path, parent metadata, or credential ACL checks fail. Its error output uses a safe error code and does not print credential content, connection details, raw client errors, or stack traces. These safeguards apply to the migration writer only; they do not configure the application runtime or Vercel environment.

Before the first apply, independently confirm the new database name and that it is empty. The writer must also verify the fixed database name, endpoint fingerprint, frozen manifest fingerprint, and empty application schema. Run its read-only verification mode first. Use the initial path only when verification reports a genuinely empty target. After an interruption, verify first: use resume only when the writer confirms an exact committed prefix under the same target and manifest; if verification reports empty, the initial path remains appropriate. Stop on any mismatch, untracked schema, incomplete control state, or invalid prefix. Never use initial mode when migration state exists.

The CLI accepts exactly one of `--verify-only`, `--expect-empty`, or `--resume`. It accepts no credential-file argument:

Run verify-only before apply and after completion. Do not change the target or manifest confirmations to bypass a mismatch.

Verify-only reports `EMPTY` for a database with no application or runner schema, `RESUMABLE_PREFIX` for an exact valid prefix, and `COMPLETE` after all 58 migrations. Any untracked schema, incomplete runner state, mismatched target/manifest, or drift is an error and requires review.

## Apply and verify

The initial run applies all 58 migrations in their frozen lexical order. It does not baseline, skip, reset, seed, or regenerate a migration manifest. The `20261004120000_separate_accounts_players` migration owns its `PRAGMA foreign_keys=OFF; BEGIN IMMEDIATE; ... COMMIT; PRAGMA foreign_keys=ON;` sequence. The runner preserves that sequence, checks the exact prior prefix/schema and empty application tables after `BEGIN IMMEDIATE`, and inserts its schema checkpoint and managed ledger rows before its `COMMIT`. The Session compatibility columns required by `20260403075615_add_test_sessions` are added inside that migration’s own write transaction. For ordinary migrations, SQL, compatibility changes, and the `_turso_sql_migrations` success row are recorded in one per-migration transaction. A known SQL failure before commit must roll that migration’s schema changes and ledger row back together.

For the managed migration, the HTTP client queues the SQL sequence and stream close on the same Hrana stream. Hrana defines a stream as one SQLite connection, stops a failed SQL sequence, and processes later close requests in order. The current open-source libSQL HTTP server handles `close` by dropping that stream’s database connection ([protocol](https://github.com/tursodatabase/libsql/blob/main/docs/HRANA_3_SPEC.md), [request dispatch](https://github.com/tursodatabase/libsql/blob/main/libsql-server/src/hrana/http/request.rs), [stream connection release](https://github.com/tursodatabase/libsql/blob/main/libsql-server/src/hrana/http/stream.rs)). SQLite automatically rolls back an open transaction when its connection is destroyed ([SQLite connection close](https://www.sqlite.org/c3ref/close.html)). These semantics support rollback for a known SQL failure before `COMMIT`. No hosted Turso migration or failure injection was run, so hosted server behavior remains unverified. If transport or process failure interrupts a batch or makes commit completion ambiguous, run read-only verification before deciding whether to resume; do not assume it rolled back or issue `ROLLBACK` on a new stream, which cannot control the original stream’s transaction.

After a successful apply, run read-only verification again. Confirm the target and manifest fingerprints, all 58 expected migration names in the managed `_turso_sql_migrations` ledger, expected schema checks, and zero foreign-key/integrity errors. The managed Turso ledger is separate from Prisma’s `_prisma_migrations`; Prisma ledger state is not evidence that this custom SQL chain ran. The normal build does not apply migrations, and `npx prisma migrate deploy` is not this Preview writer.

If a migration fails, stop and preserve its redacted output. Prior migrations that committed successfully remain committed; atomicity is per migration, not for the entire 58-migration chain. Do not reverse migrations, delete/reset the database, baseline names, skip a failed migration, or manually insert ledger rows. Run read-only verification to determine whether the database has an exact valid applied prefix under the same endpoint and manifest. Resume only through the explicit resume mode when the writer confirms that exact prefix and matching hashes; otherwise stop for review. A migration that partially changed schema without a committed ledger row requires investigation rather than an automatic retry assumption.
