## Recovery and completion

Before database freezing, failure leaves the predecessor data intact. Restoring HTTP requires verifying that no database fences exist and restoring only the pinned original firewall policy. The normal operator does not automatically reopen an uncertain cutover.

After database freeze, retain maintenance on any uncertainty. Recover forward using the same reviewed writer and matching application; do not remove fences manually. This procedure contains no pre-apply abort/thaw path, so an abort after freezing needs separate review. After migration, do not revert to the old application or drop the additive schema after collaboration writes begin. Preserve results and rating ledgers.

A failed opening attempt tries to restore the HTTP fence and reports any failure to verify that restoration. Keep protected backup, manifests, review/approval evidence and runtime records. Revoke the dedicated writer after completion. Pause the continuation only when deployment verification is complete or required user input is the only remaining action.
